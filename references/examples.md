# 实例（照着这个粒度写）

> 模式 A 仅在用户**显式**说「转成提示词 / 出个提示词卡」时使用（默认不对普通指令出卡）。

## 例 1｜模式 A：一句自然语言 → 提示词卡

**用户原话**：「帮我把那个项目的导出文件名改一下」

```
【提示词卡 · 待确认】
目标：把导出文件名里的旧品牌标识改成新标识
输入：仓库 <路径>；缺具体旧/新串 → 默认按 <旧名> → <新名>
产出：改动 diff + 实际触发一次导出的文件名证据（不落盘到项目外）
边界：只改导出文件名相关代码；白名单保留旧名（目录名、cookie 名、存储键名）；不装包、不提交
→ 回「确认」/「改：<修改点>」/「直接干」
```

要点：四要素全有；缺的信息给默认值而不是反问；把用户已生效的常驻规则（先读代码、最小变更）用「边界」一格体现，不单独列。

## 例 2｜模式 B：简单任务不要硬拆

**原提示词**：「帮我写个正则，把日志里的时间戳抽出来」

**1. 问题诊断**：目标能看懂但验收不了 —— 没说什么格式的时间戳、日志长什么样、跑在哪。属于简单任务，只需补齐输入样例和产出规格，不该拆步骤。【评分 原 42 → 优后 82】

**2. 优化后提示词**：

```
写一个正则，从日志行里抽取时间戳。

输入样例（3 行，覆盖常见格式）：
2026-09-25 14:03:11.482 INFO  ...
[2026-09-25T06:03:11Z] WARN ...
25/Sep/2026:14:03:11 +0800 ...

要求：
- 一个正则同时匹配上述三种；不匹配则返回空
- 语言：Python `re`，用命名组 time
- 输出：正则本体 + 能直接跑的 5 行验证代码 + 逐行匹配结果
- 边界：不改我的日志解析逻辑，只给正则和验证片段
```

**3. 已做假设**：日志是文本行形式（非 JSON）；三种时间格式就够覆盖；用 Python 实现（没说是哪种语言）。

**4. 关键追问**：
1. 实现语言？ a) Python `re`（我默认用这个） b) JS `RegExp` c) 其他 → 告诉我
2. 日志里的时间戳要转成统一时区吗？ a) 不转，原样抽字符串（默认） b) 全部转 UTC c) 转成 +0800

## 例 3｜模式 B：复杂多阶段 → 拆步骤 + 验收标准

**原提示词**：「把项目里的旧品牌名全换掉，两端的都换，然后验证一下」

**1. 问题诊断**：范围、旧/新名、白名单一个没说，「两端的都换」不明确是哪两端，「验证一下」无验收标准 —— 复杂任务写成了一句话，执行者只能猜。需拆成分类替换 + 双端验证两类步骤，并为每步定可判定的验收标准。【评分 原 28 → 优后 86】

**2. 优化后提示词**：

```
把仓库中的旧品牌名替换为新名，分两类处理并逐类验证。

参数（缺则按默认）：旧名 = <旧>，新名 = <新>

步骤：
1. 枚举：列出全库所有匹配旧名的文件与行号（区分代码/注释/文档/配置/文件名）。
   验收：产出一张表（路径 | 行号 | 类别 | 行内容），条数写清。
2. 分类：分为「必改」「不改」「待定」三组。
   - 不改：已列入白名单的路径/键名（请用户提供白名单）
   - 待定：字符串拼出来的名（如 'abc' + 'def'），单独列出问用户
   验收：三组清单 + 每组理由。
3. 改：只改「必改」组，逐类分开提交。
   验收：git diff 只含这些文件；无格式化/无关改动。
4. 验证（两侧各一轮）：
   - 前端：启动后页面标题、菜单、导出文件名均为新名（截图或 DOM 证据）
   - 后端：接口返回体、日志前缀为新名（贴 3 条真实输出）
   - 残留：再跑一次步骤 1 的枚举，结果应为空（贴输出）
   验收：四项均贴真实输出；任一项没证据就报「未验证」并说明为何验不了。
5. 交付：改动清单 + 每项验证证据 + 未覆盖范围（哪些没验、为什么）。

边界：不提交、不推送、不删文件、不装包；白名单内的一律不动。
```

**3. 已做假设**：无（旧/新名与白名单均以参数形式留空，由用户填入）。

**4. 关键追问**：
1. 白名单怎么给？ a) 用户直接列路径（推荐） b) 我根据现有代码报一版给用户确认 c) 按「目录名/键名不改」通例自行判定
2. 这次要一口气跑完还是每阶段停一次？ a) 一口气跑完，只在步骤 4 出问题才停（推荐） b) 步骤 2 结束后等确认 c) 每步都停

## 例 4｜模式 B：system prompt（角色类）

**原提示词**：「你是一个代码审核专家，帮我审代码」

**1. 问题诊断**：只有身份没有行为契约：审什么（安全/性能/风格）、严重度怎么定、不确定时怎么办、输出什么格式全没写，所以它只会给出泛泛建议。system prompt 的优化重心是边界与优先级，而不是堆角色形容词。【评分 原 30 → 优后 84】

**2. 优化后提示词**：

```
你是代码审核专家，对给出的 diff 做只读审核。

审核维度与优先级（高 → 低）：
1. 安全：注入、硬编码凭据、越权、不安全的反序列化
2. 正确性：边界条件、并发、错误处理缺失
3. 性能：只报可量化的（O(n²)、循环内 IO）

行为约束：
- 只审改动行及其直接上下文，不重构、不改代码
- 每条发现必附：文件:行号、严重度（严重/一般/建议）、为什么是问题、最小修法
- 不确定时写「无法判定」并说明缺什么信息，不猜
- 没发现问题就直说「未发现问题」，不凑数

输出格式：一个表格（位置 | 严重度 | 问题 | 修法），末尾一行统计（严重 N / 一般 N / 建议 N）。不写开场白和总结。
```

**3. 已做假设**：输入是 git diff（不是整个仓库）；语言不限，通用规则。

**4. 关键追问**：
1. 审核范围是只改动的 diff，还是也给架构层建议？ a) 只审 diff（推荐） b) diff + 架构建议
2. 严重度没发现问题时要不要同时给出「已验证项」清单？ a) 不要，未发现问题就一行（推荐） b) 要，列出已检查的维度
